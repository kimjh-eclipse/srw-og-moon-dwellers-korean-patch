2026-09-23 갱신. [제보 본문과 추가 댓글](https://github.com/kimjh-eclipse/srw-og-moon-dwellers-korean-patch/issues/10)을 함께 처리한다. 9월 23일 댓글까지 포함한다.

## 누적 기준과 변경 경계

편집 기준은 게시된 v20260919의 target 파일이다. 사용자 설치본의 혼재된 버전이나 일본판 번역 전 파일 위에 교정만 덮어쓰지 않는다. 배포 델타의 source는 별도로 검증한 일본판 원본이다.

| 자원 | 변경 범위 | 보존하는 구조 |
|---|---|---|
| Logic | 9개 시나리오 엔트리, 대사 필드 21개 | 필드 시작·크기, 엔트리 크기·시작 위치, `@` 줄 제어 |
| General2d | 엔트리 3751의 모드·계승·루트 안내 40개 필드 | WTD 길이 필드, NUL 종료, 색상 태그 순서·값 |
| Common / Battle / General3d / PARAM.SFO / ICON0.PNG | 변경 없음 | v20260919 target 전체 SHA-256 |

40개는 색상별 변형과 중복 UI 필드를 포함한 실제 패치 필드 수다. 고유 번역 문장 수로 해석하지 않는다. 인명은 원문에 해당 이름이 있는 대사에만 교정한다.

## 문자열이 들어가는 것과 재압축이 들어가는 것은 별개

프록시 인코딩의 바이트 길이가 텍스트 필드 안에 들어가더라도 압축된 엔트리의 물리적 크기는 커질 수 있다. 실제 초기 후보에서 Logic 엔트리 368이 기존 압축 영역을 7바이트 초과했다. 이 후보는 배포 대상으로 쓰지 않는다.

구조를 이동하거나 뒤 엔트리를 덮어써서 맞추지 않는다. 의미를 유지하는 문장 조정과 압축 후 readback 검증을 거친다. 압축 스트림 뒤 패딩을 쓰는 경우에도 해제 결과가 기대 바이트와 완전히 같아야 하며, 비압축 블록 뒤에 패딩을 더해 내용으로 읽히게 해서는 안 된다.

최종 후보는 문장 축약 없이 인명만 교정했다. 해당 엔트리의 블록 크기 합은 `11710 + 1891 + 1700`에서 `11713 + 1888 + 1700`으로 유지된다. 내용이 변경되지 않은 두 번째 블록을 더 작게 압축하여 첫 블록의 3바이트 증가를 상쇄했다. 압축 결과를 재사용할 때에도 입력 바이트와 해제 결과가 정확히 같은지 검사한다. 압축 반복 횟수를 늘리면 항상 결과가 작아지는 것은 아니므로 실제 결과 크기를 비교해야 한다.

## 완료 판정

1. 모든 편집 필드의 인코딩 길이와 제어 태그를 검사한다. 초과 시 잘라 넣지 않고 실패시킨다.
2. 재암호화한 SDAT를 다시 읽어 수정 엔트리가 예상 바이트와 같은지 검사한다.
3. 모든 비대상 엔트리는 편집 기준본과 바이트 단위로 대조한다. 엔트리 테이블과 아카이브 크기도 대조한다.
4. 원본에 배포 xdelta를 적용해 7개 target 해시를 대조한다.
5. range pack을 내장한 실제 EXE와 폴더 스크립트로 적용·복구 왕복 시험을 수행한다.
6. 패키지 내부 체크섬과 게시 ZIP의 재다운로드 해시를 대조한다.

구체적인 실행 결과와 target 해시는 [배포 검증 기록](release-validation.md)을 따른다. 이 절차는 게임 화면 시험을 대체하지 않는다. 이번 변경의 화면 검증은 별도로 1·2화, 최종화, 새 게임 모드 설명에서 수행해야 한다.

## 화수 표기와 대사 특정

제보의 화수 표기와 talk 파일 번호는 일치하지 않는다. 9월 23일 제보는 6화 지상 루트로 적혀 있으나 해당 대사는 `ls005`(카이), `ls010`·`ls029`(길리엄)에 흩어져 있다. 따라서 화수가 아니라 원문과 문맥으로 대사를 특정한다.

길리엄의 `응`은 두 곳이 후보였다. `ls029`는 프란츠가 `길리엄 예거 소령`이라 정중히 인사한 데 대한 답(원문 `ええ`)이고, `ls010`은 부하가 물러나며 하는 인사에 대한 답(원문 `ああ`)이다. 어느 쪽이 제보 화면인지 단정할 수 없어 둘 다 교정했다. 후자는 필드 예산이 12바이트라 `그래`(13바이트)가 들어가지 않으며 한 음절만 가능하다.
