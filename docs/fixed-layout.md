# 고정 배치 재빌드

초기 4개 아카이브의 델타 합계를 **667,615,879바이트에서 7,673,358바이트(약 7.32MiB)로, 약 87배** 줄인 기법이다. 아래 수치는 당시 실험 기록이며 v20260919 ZIP 크기나 현재 7개 패치 합계가 아니다.
이 프로젝트에서 가장 실질적인 성과이므로 근거가 된 측정치와 함께 남긴다.

## 문제

번역을 마친 아카이브를 표준 방식으로 재패킹하고 원본 대비 xdelta를 뜨자
델타가 원본 파일 크기와 거의 같게 나왔다.

| 파일 | 원본 크기 | 표준 재패킹본의 델타 | 비율 |
|---|---:|---:|---:|
| `Common` | 505,828,992 | 505,369,094 | 99.9% |
| `Logic` | 38,399,120 | 38,373,163 | 99.9% |
| `General2d` | 611,585,392 | 120,784,668 | 19.8% |
| `Battle` | 1,729,186,848 | 3,088,954 | 0.18% |
| | | **667.7MB** | |

암호문이라 ZIP 2차 압축도 이득이 없다. 이 상태의 `Common` 패치는 사실상 그 파일
전체를 담고 있어, 원본 게임 데이터를 배포하지 않는다는 원칙과 정면으로 충돌한다.

## 원인 규명

`Battle`은 1.7GB인데 델타가 3MB였고 `Common`은 505MB였다. 같은 도구, 같은 형식인데
차이가 세 자릿수로 벌어진 이유를 찾아야 했다.

### 1단계 — 평문 비교

`Logic`의 원본과 최종본을 각각 복호해 평문 PSARC를 비교했다.

```
평문 크기       38,323,967 (양쪽 동일)
4KB 블록 9,357개 중 일치       1개 (0.01%)
```

거의 전부 다르다. 그런데 내용이 실제로 그만큼 바뀌었을 리는 없었다.

### 2단계 — 엔트리 단위 비교

같은 두 평문을 PSARC 엔트리 단위로 풀어 비교했다.

```
전체 엔트리                    888개
내용이 다른 엔트리             269개
변경 분량 (비압축 기준)        19.82MB / 239.99MB
```

`Common`은 더 극단적이었다.

```
전체 엔트리                    1,171개
내용이 다른 엔트리             1개  →  /Dat/Font/font.bin
원본·최종 font.bin 크기        둘 다 4,294,144 바이트로 동일
```

**엔트리 하나만 바뀌었는데 파일 전체가 다른 바이트가 되어 있었다.**

### 결론

원인은 오프셋 이동이다.

1. 엔트리 하나의 내용이 바뀐다
2. 재압축하면 zlib 출력 크기가 원본과 달라진다
3. 그 뒤 모든 엔트리의 `offset`과 블록 테이블이 밀린다
4. 평문 전체가 어긋난다
5. [SDAT은 블록 독립 암호화](sdat.md#키-유도)이므로, 밀린 평문이 들어간 블록의
   암호문은 전부 무작위에 가깝게 바뀐다
6. 델타가 파일 크기에 수렴한다

`Battle`이 3MB였던 것은 이미 오프셋을 보존하는 방식으로 빌드돼 있었기 때문이다.

> **델타 크기는 "내용이 얼마나 바뀌었나"가 아니라 "평문 오프셋이 밀리지 않았나"로 결정된다.**

## 해법

블록 고정 방식은 원본 PSARC의 **TOC·블록 테이블·엔트리 오프셋·전체 크기**를 유지한다. 엔트리 구간 고정 방식은 엔트리 오프셋·전체 크기를 유지하되 엔트리 안의 블록 크기 테이블을 바꿀 수 있다. 두 방식의 보존 조건을 혼동하지 않는다.

1. 내용이 바뀌지 않은 엔트리는 **재압축하지 않고 원본의 압축 블록 바이트를 그대로 복사**한다
2. 바뀐 엔트리는 압축 결과가 원래 슬롯 크기 안에 들어가야 한다
   - 남으면 패딩
   - 넘치면 실패한다. 압축 슬롯보다 큰 raw 블록으로 바꿔 넣는 것은 해결책이 아니다. 더 작은 압축 결과, 검수된 텍스트 조정 또는 엔트리 구간 재배분을 검토한다
3. 결과를 [`sdat_encode.py`](sdat.md#재암호화와-메타데이터-위조)로 재암호화한다.
   바뀌지 않은 블록은 평문이 같으므로 암호문까지 동일해진다

### 슬롯 초과 처리

`Common`의 폰트 이식은 드라이런에서 여유가 있었다.

```
변경 블록          57개
블록 크기          65,536
고정 슬롯 초과     0개
최대 초과          0 바이트
```

`Logic`은 블록 단위로만 고정했을 때 3개 블록이 7~29바이트 초과했다.
**엔트리 전체의 물리 구간을 고정하고 그 안에서 블록 경계를 재배분**해 해결했다.
엔트리 오프셋과 전체 파일 크기는 그대로 유지된다.

### 현재 구현의 실패 조건

| 구현 | 반드시 유지 | 허용 변경 | 실패 조건 |
|---|---|---|---|
| `psarc_fixed_blocks.py` | 엔트리 비압축 크기, TOC, 블록 테이블, 각 물리 블록 용량 | 용량 안 압축 스트림·후행 패딩 | 한 블록이라도 원래 물리 용량 초과 |
| `psarc_fixed_entry_spans.py` | 엔트리 비압축 크기·물리 구간·전체 파일 크기 | 구간 내부 블록 크기·배치 | 엔트리 전체 용량 초과 또는 패딩 배치 불가 |

두 구현 모두 출력 엔트리를 다시 읽어 기대 바이트와 비교한다. 전체 비대상 엔트리 불변성은 호출하는 빌드·감사 단계에서도 검사해야 한다. 압축을 더 강하게 해 넣더라도 BMD 포인터나 태그가 잘못되면 화면은 깨질 수 있다.

이슈 #7 후속 빌드에서는 변경 엔트리 안의 미변경 블록도 재압축해 여유를 확보한 별도 처리가 있었다. 이를 모든 고정 구간 빌더가 자동 수행하는 기능으로 해석하지 않는다.

## 등가성 검증

배치만 바꾼 것이지 내용이 달라지면 안 되므로, 복호 후 엔트리를 전수 대조했다.

| 파일 | 대조한 엔트리 수 | 내용 차이 |
|---|---:|---:|
| `Common` | 1,172 | 0 |
| `General2d` | 4,636 | 0 |
| `Logic` | 888 | 0 |

여기에 더해 원본 기준 **왕복 검증**을 수행했다. 원본에 델타를 적용한 결과의
SHA-256이 최종 빌드와 바이트 단위로 일치해야 한다. 당시 4개 대상의 왕복 통과와 RPCS3 화면 확인이 기록됐다. 이것을 현재 7개 대상 전체의 게임 실행 검증이나 PS3 하드웨어 검증으로 확대하지 않는다. [현재 검증 범위](release-validation.md)를 별도로 확인한다.

## 다른 프로젝트에 옮길 때

이 기법이 성립하는 조건은 두 가지다.

- 컨테이너 암호화가 **블록 독립**일 것 (체이닝이 파일 전체에 걸치면 무의미하다)
- 아카이브가 **오프셋 테이블 기반**일 것 (순차 스트림이면 슬롯 고정이 불가능하다)

PSARC + SDAT의 이 사례는 둘 다 만족한다. 다른 타이틀에서는 압축 방식, 슬롯 여유, 패딩 허용, 무결성 검사와 실행 파일 의존성을 다시 검증해야 한다.
