# 실기 검증과 오판 정정

> 2026-09-19 정정: 이 페이지는 초기 RPCS3 백화 사례의 조사 기록이다. 제목의 “실기”는 PS3 하드웨어 시험을 뜻하지 않는다. 현재 배포의 시험 범위는 [배포 구성과 검증 범위](release-validation.md)를 따른다.

초기 배포 직전 타이틀 화면이 흰색으로 표시되는 현상이 나타났다. 아래는 그 환경에서 SPU 캐시 정리로 회복된 사례의 기록이다. 모든 백화·빈 대사창의 원인이 같다는 뜻은 아니다. 이후 전투 대사 누락은 별도의 [BMD 참조 문제](bmd-font.md)로 다뤘다.

> **이 문서는 한 번 틀렸다가 정정됐다.**
> 처음에는 원인을 "전환 중 조기 입력"으로 결론내고 그대로 배포 문서에 실었다.
> 실제 원인은 SPU 캐시 누적이었고, 조기 입력은 우연히 상관관계처럼 보였을 뿐이다.
> 잘못된 회피 방법이 공개된 채로 나갔다. 아래 §실제 원인 참조.

## 증상

1. 로고 애니메이션이 끝난 뒤 잠시 흰 화면이 나온다
2. 여기서 버튼을 누르면 화면이 검게 바뀐다
3. 타이틀 화면(`PRESS ANY BUTTON`)이 표시되지 않는다
4. 이후 메뉴는 **커서 이동·선택·사운드가 정상 동작하지만 화면만 흰색**이다

4번은 표시 경로를 우선 조사할 단서였다. 로직이 살아 있고 그림만 안 나오더라도 텍스트·스크립트 데이터 손상을 그 관찰만으로 배제할 수는 없다.

## 배제 과정

### 후보 1 — 한국어 패치 회귀

가장 먼저 의심할 대상이지만, 다음이 이미 확인돼 있었다.

- 설치 전 4개 파일 해시 = 이전에 정상 확인된 최종 빌드
- 설치 후 4개 파일 해시 = 동일한 값

파일 해시 일치는 설치 바이트가 같다는 뜻이지 실행 결과가 항상 같다는 뜻이 아니다. 설정·캐시·참조하는 다른 자원·실행 상태는 달라질 수 있다. 당시 원본 4개로 되돌려 재현했고 **원본에서도 동일하게 발생**했다.

→ 배제.

### 후보 2 — 게임 데이터 누락

HDD 설치본에 `Sound.psarc`, `Movie.psarc`, `PSARCLIST.BIN`이 없었다.
로그에도 `CELL_ENOENT`가 찍혔고, 직후 `MoviePlayer` 스레드와 `libsail`(동영상 재생 모듈)이
뮤텍스 오류를 뱉었다. 오프닝 동영상을 못 읽어 화면이 멈추는 그림과 맞아 보였다.

ISO에서 세 파일을 추출해 설치하고 재현했다. **동일했다.**

→ 배제.

> **여기서 오판이 하나 있었다.** 로그의 `dev_bdvd` 폴백 실패 라인은 `Dat/` 하위
> 텍스처와 디렉터리 건이었는데, 이를 `Sound`/`Movie`까지 일반화해 "디스크 폴백도
> 실패했다"고 적었다. 실제로는 폴백이 정상 동작하고 있었다. 발췌 몇 줄로 전체를
> 단정한 것이 잘못이었다.

### 후보 3 — 에뮬레이터 버전 회귀

실행 중인 RPCS3가 폴더 이름(`v0.0.27`)과 달리 **v0.0.42-19699**였다.
`rpcs3.exe`가 검증 시점 전후로 교체된 이력이 있어 회귀를 의심했다.

이전 버전에서도 동일하게 재현되는 것이 확인됐다.

→ 배제.

### 후보 4 — 전환 중 조기 입력 (한때 결론으로 채택했으나 오판)

세 후보가 모두 빠지고 남은 변수가 조작 타이밍처럼 보였다.
흰 화면에서 기다리면 정상, 먼저 누르면 재현되는 것처럼 관찰됐다.

이것을 결론으로 삼아 배포 문서에 "버튼을 누르지 말고 기다리세요"라고 적었다.
**틀렸다.** 캐시 상태에 따라 증상이 나타났다 사라졌다 하는 것을 조작 타이밍의
차이로 오인한 것이다.

→ 배제.

### 실제 원인 — RPCS3 SPU 캐시 누적

원인은 게임 데이터가 아니라 **에뮬레이터가 쌓아 둔 SPU 캐시**였다.

```
<RPCS3>\cache\BLJS10335\ppu-<해시>-EBOOT.BIN\spu-safe-v1-tane.dat
```

이 파일을 지우고 다시 실행하면 화면이 정상으로 돌아온다.
RPCS3 게임 목록에서 해당 게임 **우클릭 → Remove → Remove SPU Cache** 로 지울 수 있다.

**한 번 지우면 끝나지 않는다.** 플레이를 계속하면 캐시가 다시 쌓이면서 재발한다.
증상이 보이면 그때마다 지우면 된다.

PPU 캐시(`*.obj.gz`)와 셰이더 캐시는 이 문제와 무관하다.

#### 앞선 관찰이 전부 설명된다

SPU 캐시는 **게임 데이터와 무관하게 타이틀 단위로 유지된다.** 그래서

- 원본 `.sdat`로 되돌려도 재현됨 → 캐시가 그대로 남아 있었기 때문
- RPCS3 버전을 바꿔도 재현됨 → 캐시가 그대로 남아 있었기 때문
- 해시가 동일한 파일에서 결과가 달라짐 → 파일이 아니라 캐시 상태의 차이
- 될 때와 안 될 때가 있음 → 조작 타이밍이 아니라 캐시 누적 정도의 차이

"한국어 패치와 무관하다"는 판정은 처음부터 맞았다. 원인과 회피 방법만 틀렸다.

#### 설치 스크립트 반영, 그리고 되돌림

`v20260813` 의 `install.ps1` 은 패치 적용 후 이 게임의 `spu-*.dat` 를 삭제했다.

**`v20260814` 에서 이 동작을 뺐다.** 캐시는 사용자 환경에 속하고, 설치 스크립트가
말없이 지우고 다닐 대상이 아니다. 캐시를 지워야 하는 상황은 백화가 실제로 보일 때뿐이고,
그때는 RPCS3의 `Remove SPU Cache` 를 쓰는 편이 범위가 분명하다.

현재 `install_xdelta.ps1`은 캐시를 정리하지 않는다. 반면 ISO 빠른 패처에는 설치 데이터와 루트 SPU 캐시 파일을 정리하는 옵션이 있다. 폴더 직접 패치에는 적용되지 않으며 하위 SPU 캐시까지 재귀 처리하지 않는다. 세이브는 정리 대상이 아니다. [설치 안내](install.md)의 적용 경로별 절차를 따른다.

## 로그 대조

패치본 세션과 원본 세션의 RPCS3 로그를 대조했다. 오류 프로필이 한 줄씩 대응했고,
양쪽 모두에서 다음이 **없었다**.

- SDAT 복호 실패
- PSARC 파싱 실패
- Fatal / Assertion

이 로그에서는 해당 오류를 찾지 못했다. 오류 로그의 부재만으로 모든 엔트리·대사 참조가 정상이라고 입증되지는 않는다.

## 배운 것

**동일 해시 파일에서 다른 결과가 나오면 파일 교체 여부와 별개로 환경·캐시·다른 자원·실행 경로를 대조한다.** 같은 데이터 안에서도 정상 분기와 손상된 분기가 공존할 수 있으므로 파일 내용 검사를 생략하지 않는다.

해시 대조를 설치 전후 양쪽에서 해 두지 않았다면 이 판단에 훨씬 오래 걸렸을 것이다.
검증 절차에 해시 기록을 넣어 두는 것은 원인 규명 비용을 크게 줄인다.

또 하나. **원인 추적 중에 나온 관찰을 결론으로 승격시키지 않는다.**
`Sound`/`Movie` 누락은 사실이었지만 원인은 아니었고, 폴백 실패는 사실도 아니었다.
로그 발췌 몇 줄에서 전체를 단정하면 이렇게 어긋난다.

가장 비싼 교훈은 마지막에 나왔다. **남은 후보가 하나뿐이라는 이유로 그것을 결론으로
삼으면 안 된다.** 세 후보를 배제하고 남은 "조기 입력"을 검증 없이 결론으로 올렸고,
그 잘못된 회피 방법이 공개 문서에 실려 배포됐다. 소거법으로 좁힌 마지막 후보도
**직접 증명해야 결론이 된다.** 여기서는 캐시를 지웠다 남겼다 하며 대조하면 됐을 일이었다.

## 배포 판정

당시 원본에서도 재현되고 캐시 정리로 회복된 사례는 알려진 문제로 안내했다. 이 과거 판단을 새 증상에 자동 적용하지 않는다. 화면을 확인할 수 없으면 정상 진행을 보장할 수 없으며, 새 회귀는 파일 조합과 재현 조건부터 다시 검사한다.

단, 다음은 계속 실패로 판정한다.

- 게임 데이터 손상 경고
- 크래시
- 기다려도 타이틀이 영구히 표시되지 않는 경우
